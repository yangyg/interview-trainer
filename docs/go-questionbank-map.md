## 2 六层知识骨架

### L1 语言语义 · 86 题

链条:**值语义 → slice 头部 → map 结构 → string → defer → panic/recover → interface → 方法集 → range → 闭包 → 声明与常量 → 泛型 → 错误处理 → 内存对齐 → 代码输出**

| 知识点 | 题库里被追问到什么程度 |
|---|---|
| slice | 头部是 `{ptr,len,cap}` 24 字节;扩容阈值与 Go 1.18 后 256 以上改为平滑增长;共享底层数组三坑(append 覆写、旧切片拖住大数组、copy 不等于隔离);nil/空/零切片三者区别 |
| map | hmap + bmap、负载因子 6.5 的由来、翻倍与等量两种扩容、渐进式搬迁 evacuate、key 必须可比较、并发写 panic 的检测开关 |
| string | 不可变性与 `{ptr,len}`、`[]byte` 零拷贝转换(`unsafe` / `strings.Builder`)、byte 与 rune、`len("中文")`=6 |
| defer | 注册链 LIFO、参数即时求值、与命名返回值的配合、open-coded defer 的触发条件、循环里 defer 的坑 |
| interface | iface(带方法)与 eface(空接口)、typed nil 不等于 nil、方法集决定谁实现接口、接口比较的运行期 panic |
| range / 闭包 | Go 1.22 循环变量 per-iteration 的语义变化、range 是值拷贝、遍历中增删元素的行为、闭包捕获的是变量不是值 |
| 代码输出题 | 17 道,覆盖 defer 链、变量遮蔽、常量溢出、slice append 覆写、typed nil、循环 + goroutine、panic 覆盖 |

### L2 并发模型 · 50 题

链条:**进程/线程/协程 → GMP → work stealing / hand off → 抢占 → GOMAXPROCS → 栈管理 → 泄漏 → hchan → select → happens-before → Mutex/RWMutex → Once/Pool/atomic/Cond → context → 并发控制**

- **调度**:G/M/P 三者职责;`go func()` 后一条 G 的完整生命周期;findRunnable 的查找顺序(本地队列 → 全局队列 → netpoll → 偷);1.14 之前的抢占失效原因(只有函数调用才有协作点);容器里 GOMAXPROCS 与 cgroup 的关系(Go 1.25 的变化)。
- **channel**:hchan 七字段(`qcount/dataqsiz/buf/sendx/recvx/sendq/recvq/lock`);发送/接收的四条分支(直接拷贝 → 等待队列 → 缓冲区 → 阻塞);已关闭 channel 的读写行为表;nil channel 的阻塞特性与「用 nil 屏蔽 select 分支」技巧;select 多 case 就绪时随机。
- **同步原语**:Mutex 正常模式与饥饿模式切换(1ms 阈值)、不可重入不可复制、自旋条件;RWMutex 写饥饿;WaitGroup 三种误用;sync.Pool 两次 GC 清空、不能当长期缓存;atomic 与 atomic.Value 的类型一致性约束。
- **并发控制**:context 四种派生与取消传播;限并发的四种写法(带缓冲 channel 信号量 / errgroup.SetLimit / worker pool / 令牌);errgroup 的「任一失败即取消」。

### L3 运行时 · 29 题

链条:**内存分配器三级结构 → tiny object → 逃逸分析 → 三色标记 → 漏标两条件 → 混合写屏障 → 触发与调参 → STW → 不分代 → RSS 不降 → pprof**

- 分配:mspan/mcache/mcentral/mheap 三级;mcache 挂在 P 上所以免锁;微对象(<16B 且无指针)合并分配。
- 逃逸:`go build -gcflags="-m"` 验证;接口赋值、返回指针、闭包捕获、切片扩容、大小不定是五类典型逃逸。
- GC:三色不变式;漏标必须同时满足「黑色对象新增指向白色对象的引用」且「灰色对象到白色对象的引用被删除」;Go 1.8 混合写屏障同时兼顾两点,因此无需 STW 重扫栈;GOGC 百分比与 GOMEMLIMIT 软上限的配合;STW 只发生在标记准备与标记终止两处。
- 观测:`GODEBUG=gctrace=1`、`go tool trace`、pprof heap/profile;RSS 高而 heap 低的三类原因(未归还 OS、cgo/线程栈、外部内存)。

### L4 系统工程 · 72 题

链条:**netpoll → TCP → HTTP/HTTPS → gRPC → net/http 客户端与服务端 → database/sql → 优雅退出 → go mod/MVS → 日志 → pprof/benchmark → 压测与容量 → 存储中间件 → 容器交付**

- **网络**:少量线程撑大量连接靠 netpoll + 非阻塞 IO;TCP 握手挥手、TIME_WAIT 2MSL、拥塞控制、最大连接数的瓶颈(端口/文件句柄/内存);HTTP/1.1 与 2 与 3 的队头阻塞差异;HTTPS 证书验证链;gRPC 基于 HTTP/2 多路复用 + Protobuf 二进制;粘包的三种解法。
- **工程细节**:`http.Client` 必须设的四类超时与 `MaxIdleConnsPerHost`;`resp.Body` 不读完就 Close 会毁掉连接复用;`database/sql` 的 `SetMaxOpenConns / SetMaxIdleConns / SetConnMaxLifetime`;`time.After` 在循环里的定时器泄漏;MVS 最小版本选择;`slog` 结构化日志。
- **性能**:pprof 五种 profile 的分工;火焰图读法;benchmark 的 `-benchmem` 与编译器优化导致的失真;锁竞争的定位;`[]struct` 与 `[]*struct` 的取舍;高频路径降分配手段。

### L5 分布式架构 · 59 题

链条:**CAP/BASE → 幂等 → 分布式锁 → 分布式事务 → 一致性哈希 → 限流 → 熔断 → 降级 → 超时与重试 → 注册发现/负载均衡 → 链路追踪 → MQ 可靠性 → 缓存三问题与一致性 → 热 key/大 key → 分库分表 → Raft**

- 请求生命周期是这一层的总线:**限流 → 熔断检查 → 带 deadline 调用 → 失败重试(带幂等键) → 降级兜底**,几乎每道场景题都可以挂在这条线上。
- 系统设计 6 题(短链、排行榜、秒杀、延迟队列、Top-K、树形评论)+ 4 道工程向(限流器、无锁 HashMap、千万连接推送、API 网关)+ 1 道算法(会议室),答案普遍给出「分层 + 取舍 + 失败模式」三段式。

### L6 表达与项目 · 8 题

项目叙事(一句话背景 → 职责边界 → 具体难点 → 量化结果 → 反思)、故障复盘、技术选型、Go 的取舍、**AI 写码的验收流程**(2026 新增考点)、跨角色冲突、反问清单。

## 4 盲区:三类缺口

### B. 薄覆盖(≤4 题)

### C. 数据缺口(不影响知识,影响产品体验)

1. `go-04`、`go-05` 共 35 题**零来源链接**,与精编题库的可信度不一致。
2. 127 题**无难度值**,导致按难度筛选时这半壁江山直接消失。
3. 57 题**无频次**,「高频优先」的排序逻辑对分册失效。
4. 124/304 题标签为「通用」,标签筛选形同虚设。
