02最致命的单点：加粗通胀

这是全篇最大的可读性杀手，也是唯一一个「改一处、通篇受益」的问题。

P0

66.4% 的文字是加粗的，平均每 32 字一次

夸张吗？不夸张。全课 15952 字，落在 **…** 里的是 10599 字，共 497 处加粗标记。渲染出来的效果是：满屏黑体，读者的眼睛找不到落点，只能从头读到尾——这正是「读不下去」的生理原因。

原文（第 0 区块）
C(Consistency,一致性):这里的「一致性」特指线性一致性(linearizability)——所有节点在任意时刻看到的都是同一份、最新的数据… 它既不是数据库的约束一致性,也不是「约束不被破坏」,更不是「副本最终会一样」——那叫最终一致,和 CAP 的 C 恰好相反。

整段只有「那叫最终一致，和 CAP 的 C 恰好相反」值得强调，其余全是底噪。当强调密度超过 15%，强调就变成了排版噪音。

现在 · 66% 加粗

C(Consistency,一致性):这里的「一致性」特指线性一致性(linearizability)——所有节点在任意时刻看到的都是同一份、最新的数据。它既不是数据库的约束一致性,也不是「约束不被破坏」。

目标 · 10% 加粗 + 一层语义色

CAP 里的 C 专指 线性一致性（linearizability）：读到的必须是最新写入的值。它不是数据库的约束一致性，也不是「副本最终会一样」——后者叫最终一致，和 CAP 的 C 恰好相反。

右边这版只做三件事：只加粗术语（线性一致性）、用紫色底色标出「这一课的新概念」（最终一致）、用红色标出「常被答错的点」（不是）。密度从 66% 降到 10%，信息量反而变多了——因为读者终于知道该看哪儿。

03五条标准逐项核对

6.8

通俗易懂：概念精度很高，但门槛一上来就在天花板

做得好的：开篇第一句就拆穿误读——「绝大多数错误回答都从背错定义开始」。这是很好的判断，直接把读者从「背书模式」拽到「理解模式」。限流那节用「一起变慢比拒绝一部分更糟」解释雪崩，也很到位。

问题一：没有入口场景。全文第一个词就是 C/A/P 三个字母。读者没有任何「我遇到过这个问题」的锚点，只能从抽象定义开始爬。而这一课最适合的开场其实是一个具体场面：双十一零点，北京机房和上海机房的网络断了 3 分钟，用户下单会怎样？——一句话就把分区、可用性、一致性全带出来了。

问题二：整课 0 个类比。20 个区块里 analogy 计数为 0。全站 147 课有 55 课是这样，这一课只是其中最典型的一篇。而分布式恰恰是最需要生活类比的领域——「分布式锁」可以类比成酒店房卡，「最终一致」可以类比成两家分行事后对账，「幂等」可以类比成存支票时柜员核对流水号。现在这些位置全部由抽象描述硬填。

8.4

由浅入深：坡度对，但缺少「先跑通再打补丁」的两段式

做得好的：区块顺序是一条清晰的认知链——定义 → 纠正误读 → 为什么只能选 AP → 靠什么收敛 → 事务谱系 → 幂等 → 锁 → 哈希 → 限流 → 熔断 → 超时重试。从「一个词」推到「一套体系」，没有跳跃。

可以更好的：现在是「一次讲到位」，缺了两个特别好用的手法。

① 版本演进式：分布式锁那节其实有这个骨架（SETNX+EXPIRE → 一条命令 → value 唯一 → Lua 比对 → fencing token），但写成了平铺的五段，没有把「为什么每一版都不够」做成显式的闯关感。加一句「到这里，90% 的人以为完事了——但下面这个坑，连 Redis 官方文档都不提」，节奏立刻不一样。

② 反事实提问：一致性哈希那节写了「3 台扩到 4 台，75% 迁移」，很好。但没有紧接着问「那如果我不扩容，只加一台只读副本呢？」——一个反问就能把「一致性哈希解决的是分配，不是扩容」这个边界钉死。

9.2

深入原理：这是全课最强的一项，已经到机制层

举三处真正「往下挖了一层」的地方，这些是拉开分档的关键，值得保留并复制到其他课：

① Redlock 的争议——不回避「这个方案有争议，Kleppmann 那篇质疑值得读」，并给出工程结论：要锁的正确性就用 etcd，只是防重复劳动 Redis 够用。这种「有争议就说有争议」的态度，比给一个干净答案更值钱。

② P2C 为什么存在——「纯随机会出现羊群效应：所有请求涌向此刻最空的机器，把它立刻打满」。这句话把一个算法存在的理由讲透了，而不是罗列「轮询/加权/最少连接/哈希/P2C」五个名词。

③ 漏桶与令牌桶的唯一区别——「桶里能不能攒令牌」。一句话说清两个容易混的算法，这是高手的写法。

唯一的遗憾：深是深在「文字」里，没有深在「图」里。4 个图示全是结果快照（矩阵表、flow 链条、时序、状态机），没有一个展示内部结构——比如 Redis 主从复制丢锁那一刻，主库内存里的 key、从库的 key、客户端的持锁认知，这三者的错位没有一张图能看见。

7.8

发散联想：边界说得很好，横向串联还不够

做得好的：一致性哈希那节主动划边界——「它只解决分配，不解决热点」，并且补了 Redis Cluster 用 16384 槽而不是一致性哈希。这是典型的「一个好答案后面还有一句」，面试里就是拉开差距的那句。

不足：联想基本是「同层横向」（CAP → 各种中间件选型），缺少三种更高级的联想：

① 跨课纵向：这一课讲了 Redis 分布式锁，但没回头指向前置的「Redis 单线程模型」——锁的「原子性为什么必须靠一条命令」根因在单线程，两课之间应该有一根线。

② 反向联想：「如果没有分布式锁，这个业务会怎么坏？」——现在只从「怎么加锁」正向讲，没有让读者体验「不加会死得多惨」。

③ 延伸到真实系统：熔断三态机讲得很完整，但没有一处提「Envoy / Sentinel / gobreaker 分别怎么实现这三态、参数叫什么」。面试官追问「你用过什么」，答不出来就白讲了。

3.8

表现手段：只有「字」和「表」，没有颜色语义、没有动画、没有交互

这是得分最低的一项，也是离用户要求最远的一项。逐项对照：

手段当前实现缺什么
颜色区分只有灰阶层级 + 主题紫，语义色仅出现在 split 区块没有「关键结论 / 易错 / 坑 / 结论」四类语义色

04三个根因

表面是「写得不生动」，往下追三层，其实是三个结构性问题。

根因一

写入流程里没有「类比」和「为什么」这两个必填位

校验脚本要求 concept + principle + question 必填，analogy 只是「三选一」里的可选项。于是写作时最省力的路径就是——能不加类比就不加。结果：全站 1362 个区块里 analogy 只有 71 个（5%），why 只有 10 个（0.7%）。用户要的「是什么、为什么、更深的原理」，中间的「为什么」几乎是空的。

根因二

强调手段只有一种，而它被用到了 66%

行内标记只支持 **粗体** 和 `代码`。当作者想强调时，唯一的动作就是加粗——497 次之后，这个动作失去了意义。缺的不是「更努力地写」，而是多两种标记：一种标「关键结论」，一种标「容易答错」。

根因三

图示是「静态快照」，不是「过程」

9 种图示类型全部是一次性渲染的静态结构。分布式、并发、GC 这类主题的本质是状态随时间变化，而静态图恰好把这个维度丢掉了。锁过期那个时序图已经画到了 6 条消息，但读者看不到「时间往前走」——这恰恰是理解「为什么会误删」的关键。

06改写示范：把 CAP 那段变成能读懂的样子

同样的知识点，换一套写法。注意它做了什么：先用生活场景兜住，再给术语，最后落到「面试怎么答」。

重写 · CAP 的三个字母

钩子一家银行在北京、上海各有一个分行，各自记账，中间靠一条电话线对账。某天电话线被施工挖断了。

冲突这时上海来了一位客户要取 10 万。柜员有两个选择：一是告诉他「系统故障，今天办不了」；二是照本地账本先给钱，等电话通了再和北京对账。前者让客户当场炸毛，后者可能出现「同一笔钱被取两次」。

术语这就是 CAP：电话线断掉叫 P（分区容忍）；「今天办不了」是选了 C（一致性）——宁可拒绝，也不让两边账本不一样；「先给钱再对账」是选了 A（可用性）——宁可短暂不一致，也要能办业务。

纠错所以「CAP 三选二」是错的。你没法要求「电话线别断」——它由施工队和天气决定。P 不是选项，是前提。真正要你选的只有一句：断线那一刻，你要一致还是要可用？

加深注意 C 的精确含义：它要求「任何时刻读到的都是最新值」，这叫线性一致性。它和「最终一致」恰好相反——后者正是「先给钱，今晚对账」的那条路。

这一版把原文 640 字压到 300 字，但多了四样东西：一个能记住的场面、一组一一对应的术语映射、一句纠错、一句可直接背下来的句式。加粗密度从 66% 降到 8%。
